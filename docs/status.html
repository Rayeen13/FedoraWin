Alpha status.

A public progress report: what is already coherent enough to demonstrate, what remains experimental, and what still blocks a release build.

Is FedoraWin ready to showcase?

Yes — as a pre-beta development preview.

The core shell now behaves coherently enough to demonstrate from the packaged FedoraWin.exe, while the project still needs broader real-device and multi-monitor hardening before a beta label.

The strongest showcase points are native DWM styling on real HWNDs, live DWM window previews in Activities, a persistent GNOME-style dock, Super/Alt+F1 Activities entry, adaptive Quick Settings, app-grid/search integration, and the explicit reversible safety model.

Working well enough to demonstrate

  • GNOME-inspired top panel with reserved desktop work area.
  • Native DWM styling on real windows while preserving caption buttons, hit-testing, Snap and resize behavior.
  • Activities with real DWM live-window thumbnails and a compact workspace strip.
  • Activities entry from panel click, Alt+F1 and safely registered left/right Super where Windows permits it.
  • GNOME-style favorites + running-app dock shared by Activities and an optional persistent desktop dock.
  • Paged application grid and Windows application discovery with GNOME-friendly aliases.
  • Adaptive Quick Settings that hide unavailable hardware controls instead of exposing dead tiles.
  • Light/dark/system appearance, accent propagation, recovery tooling and explicit non-destructive boundaries.

Still evolving

  • Workspace motion, drag/drop and transitions need more GNOME-like fidelity.
  • Quick Settings behavior still depends on the hardware and APIs Windows exposes safely.
  • Multi-monitor AppBar/work-area behavior needs broader runtime coverage.
  • App icon/focus matching still has Windows edge cases to harden.
  • Some Windows-native UI will remain visible by design; FedoraWin should integrate it cleanly rather than fake unsupported state.
Pre-beta still means visible rough edges are expected.

A clean CI screenshot is evidence of a working shell path, not proof of production reliability on every PC.

Release gates

A downloadable public release should wait until these gates are satisfied:

  1. Windows PowerShell 5.1, WPF and native compile/runtime CI is green for the exact release snapshot.
  2. Activities open/close and workspace switching are stable across repeated runs.
  3. Recovery is tested from failure states, not just normal exit.
  4. Quick Settings falls back safely when a hardware/API capability is unavailable.
  5. Packaging is repeatable and does not require destructive Windows changes.

Testing position

The development branch is gated on a real Windows runner: safety/structure regression tests, native bridge compilation, real installed-app discovery, Windows PowerShell 5.1/WPF smoke tests, packaged EXE build, and an automated launch of FedoraWin.exe all run before UI evidence is accepted.

The capture gate rejects a visible Windows taskbar, validates Activities/app-grid/Quick Settings surfaces from the real shell, and requires dark/light Quick Settings to produce a real visual change. This is stronger evidence than a preview renderer, but it still does not replace physical-device checks for Snap, multi-monitor work areas, radio hardware, brightness, audio devices or long interactive sessions.

Most useful alpha feedback

  • Activities crashes, focus problems or keyboard toggle inconsistencies.
  • Window caption/Snap/resize regressions after native styling.
  • Multi-monitor panel/work-area behavior.
  • App discovery misses, especially common aliases such as Terminal.
  • Quick Settings controls that show stale or incorrect Windows state.
  • Light/dark/accent mismatches across shell surfaces.
