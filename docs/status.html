0.4.0-dev · GNOME 51 target · pre-beta

Development status.

FedoraWin DE targets the GNOME 51 interaction and visual baseline while keeping Windows as the underlying platform. FedoraWin Shell owns the visible desktop presentation: panel, Activities, app grid, workspaces, calendar and Quick Settings. Development is active on dev/gnome-native-20260914; the site now hydrates its visual proof from the latest successful real FedoraWin.exe Windows capture set.

Working now

  • Native Rust/Win32 top panel; no always-resident WebView2 process is required for idle shell chrome.
  • Activities, app grid, search, calendar and Quick Settings are created through Tauri/WebView2 only when needed and closed when dismissed.
  • Windows installed-app discovery and GNOME aliases such as Terminal, Files and System Monitor.
  • Real HWND/DWM frame styling through reversible DWM attributes while Windows keeps native caption buttons, non-client hit testing, Snap, resizing and keyboard behavior.
  • System appearance mode leaves Windows authoritative unless FedoraWin Light or Dark is explicitly selected.
  • Top work-area reservation through Windows AppBar APIs.
  • FedoraWin DE presentation mode hides the visible Explorer taskbar while FedoraWin runs, without terminating Explorer; a separate recovery process restores the original taskbar windows if FedoraWin exits.
  • Per-monitor bounds, DPI and primary-display discovery, including negative coordinates and ultrawide geometry.
  • Live shell reflow when display topology changes.
  • Global Alt+F1 Activities hotkey through RegisterHotKey.
  • Native Wi-Fi radio state/control through the Windows WLAN API, including current connected SSID and adapter description in a GNOME-style detail flyout.
  • Real master-volume read/write through the Windows Core Audio endpoint API.
  • Real battery/AC/charging state through GetSystemPowerStatus, surfaced in Quick Settings and the native top panel.
  • Native Windows Power Mode read/write for Best Power Efficiency, Balanced and Best Performance, exposed through a GNOME-style detail flyout.
  • Internal-display brightness read/write through the Windows WmiMonitorBrightness/WmiSetBrightness provider, with the slider synchronized to the confirmed Windows value.
  • Bluetooth radio enumeration/state/control through Windows.Devices.Radios, with a GNOME-style detail flyout and graceful unavailable/denied states.
  • Wireless Pause coordinates only supported Wi-Fi and Bluetooth radios, confirms each result and stores their prior states for restoration during the running session; it does not set Windows system-wide Airplane Mode.
  • Live DWM-backed Activities previews for real top-level application windows.
  • WinEvent-driven Activities refresh for external window lifecycle changes.
  • Real Activities window activation and close actions against underlying HWNDs.
  • Windows virtual-desktop identity for real windows, including current-workspace state.
  • FedoraWin workspace move journal with an explicit undo path for FedoraWin-initiated moves.
  • Activities previous/next workspace controls switch real Windows virtual desktops.
  • The Activities startup frame no longer exposes a persistent “Loading workspace…” message; it uses a neutral GNOME-like workspace preflight until native data replaces it.

Partial or scaffolded

  • Real previous/next workspace navigation works; GNOME-style dynamic workspace creation/removal, drag-between-workspaces and continuous overview transitions are not complete yet.
  • Bare Super interception is intentionally deferred until normal Win shortcuts can be preserved.
  • Windows system-wide Airplane Mode is not implemented; Wireless Pause only manages Wi-Fi/Bluetooth and its restore journal is session-scoped. Wi-Fi radio/SSID reporting, internal-display brightness and Bluetooth radio control still need physical hardware/permission validation beyond the Windows CI environment.
  • Multi-display geometry exists, but broad physical multi-monitor hardware testing is still required.
  • Native DWM frame styling uses an independent write-ahead recovery guardian; a Windows CI force-kill test has passed on a real WinForms HWND. Physical Windows validation remains required.
  • Touchpad gestures, hot corner, notification ingestion and legacy tray compatibility remain future work.

GTK4/libadwaita HWND: Windows CI passed

Native branch commit 855cd4b compiles a FedoraWin-owned GTK4/libadwaita executable on MSYS2 UCRT64, starts the genuine AdwApplicationWindow/AdwHeaderBar on Windows, and captures dark and light 850×570-pixel HWNDs. Verified native workflow ↗ · Dark/light capture artifact ↗.

This is an isolated native proof, not yet the default window implementation. Third-party Windows HWNDs still receive only reversible DWM styling; GTK cannot turn their Windows caption controls into Adwaita. The 32 MB idle shell measurement excludes this optional native proof.

Optional third-party frame engine

Stage 1 verified: actual Win32 attach / detach / reattach

A disposable test window now runs a native-painted Adwaita-style frame and restores its original WNDPROC and Windows title bar in the same process, with unchanged style bits, header dragging and button/resize hit tests. The original and restored Windows screenshots match. Successful test and screenshot artifact ↗ · Implementation and risk contract →.

Cross-process app injection remains unimplemented

Opera GX and other custom-styled apps remain excluded. No helper is injected into unrelated applications; this technical prototype is not the final visual treatment or a beta feature. No guaranteed zero-risk or app-restart-free recovery is claimed after crash/hang. Current DWM treatment remains the reversible fallback.

Memory budget

Latest verified sampled idle: 32 MB

Windows CI launches the optimized release build and measures the FedoraWin process tree. Windows CI measured 32 MB of process-tree working set across three FedoraWin processes for the optimized release build. This is a sampled runner baseline, not a physical-device or long-session measurement.

The design target remains roughly 100 MB or less during normal idle use, with a hard automated ceiling of 300 MB. Rich WebView2 surfaces are temporary and should not stay resident after dismissal.

Immediate engineering priorities

  1. Build and validate a disposable-app native Adwaita-style frame prototype before considering any optional per-app in-process attachment; preserve custom chrome and prove disable/restore behavior.
  2. Integrate real Adwaita into a FedoraWin-owned surface without loading GTK into the idle top panel; verify process-tree memory, DPI, accessibility, resize and Snap behaviour.
  3. Validate Wi-Fi, internal-display brightness and Bluetooth radio control on physical laptop hardware, then evaluate system-wide Airplane Mode separately rather than claiming Wireless Pause is equivalent.
  4. Expand the real workspace identity layer into GNOME-style dynamic workspace and move behavior.
  5. Harden DWM thumbnail lifecycle, resize and multi-monitor placement.
  6. Continue search-provider architecture for apps, windows, settings and future providers.
  7. Implement safe Super-key behavior without breaking Windows shortcuts.
  8. Refine GNOME 51 transitions and interaction details under the existing memory budget.

Release gates

Automated Windows gate

Every native-branch push is checked for UI syntax, GNOME/UI contracts, Rust unit tests, cargo check, rustfmt, optimized release build, process-tree memory budget and real executable screenshot capture. A successful capture run also refreshes the public runtime gallery.

Still required before FedoraWin DE beta

Real Adwaita production-surface integration and complete GTK memory/dependency measurement, separately verified optional frame-engine recovery if that feature is to ship, physical multi-monitor testing, mixed DPI, docking/hot-plug, high refresh displays, long-session recovery, touchpad behavior, broader device-control coverage and a coherent end-to-end GNOME 51 interaction pass. Verify transparent popover edges and DWM behavior on a real Windows 11 GPU before using the beta label.

A green build is necessary, not sufficient. FedoraWin DE will not be called beta until the Activities/workspace/dash/search/app-grid/calendar/Quick Settings experience and recovery behavior are coherent enough for local testing without treating the user’s Windows installation as the test harness.
