0.4.0-dev · GNOME 51 target · pre-beta

Development status.

FedoraWin targets the GNOME 51 interaction and visual baseline while keeping the Windows shell underneath intact. Development is active on dev/gnome-native-20260914; the site now hydrates its visual proof from the latest successful real FedoraWin.exe Windows capture set.

Working now

  • Native Rust/Win32 top panel; no always-resident WebView2 process is required for idle shell chrome.
  • Activities, app grid, search, calendar and Quick Settings are created through Tauri/WebView2 only when needed and closed when dismissed.
  • Windows installed-app discovery and GNOME aliases such as Terminal, Files and System Monitor.
  • Real HWND/DWM frame styling through reversible DWM attributes while Windows keeps native caption buttons, non-client hit testing, Snap, resizing and keyboard behavior.
  • System appearance mode leaves Windows authoritative unless FedoraWin Light or Dark is explicitly selected.
  • Top work-area reservation through Windows AppBar APIs.
  • Per-monitor bounds, DPI and primary-display discovery, including negative coordinates and ultrawide geometry.
  • Live shell reflow when display topology changes.
  • Global Alt+F1 Activities hotkey through RegisterHotKey.
  • Native Wi-Fi radio state/control through the Windows WLAN API, including current connected SSID and adapter description in a GNOME-style detail flyout.
  • Real master-volume read/write through the Windows Core Audio endpoint API.
  • Real battery/AC/charging state through GetSystemPowerStatus, surfaced in Quick Settings and the native top panel.
  • Native Windows Power Mode read/write for Best Power Efficiency, Balanced and Best Performance, exposed through a GNOME-style detail flyout.
  • Internal-display brightness read/write through the Windows WmiMonitorBrightness/WmiSetBrightness provider, with the slider synchronized to the confirmed Windows value.
  • Bluetooth radio enumeration/state/control through Windows.Devices.Radios, with a GNOME-style detail flyout and graceful unavailable/denied states.
  • Wireless Pause coordinates only supported Wi-Fi and Bluetooth radios, confirms each result and stores their prior states for restoration during the running session; it does not set Windows system-wide Airplane Mode.
  • Live DWM-backed Activities previews for real top-level application windows.
  • WinEvent-driven Activities refresh for external window lifecycle changes.
  • Real Activities window activation and close actions against underlying HWNDs.
  • Windows virtual-desktop identity for real windows, including current-workspace state.
  • FedoraWin workspace move journal with an explicit undo path for FedoraWin-initiated moves.
  • Activities previous/next workspace controls switch real Windows virtual desktops.
  • The Activities startup frame no longer exposes a persistent “Loading workspace…” message; it uses a neutral GNOME-like workspace preflight until native data replaces it.

Partial or scaffolded

  • Real previous/next workspace navigation works; GNOME-style dynamic workspace creation/removal, drag-between-workspaces and continuous overview transitions are not complete yet.
  • Bare Super interception is intentionally deferred until normal Win shortcuts can be preserved.
  • Windows system-wide Airplane Mode is not implemented; Wireless Pause only manages Wi-Fi/Bluetooth and its restore journal is session-scoped. Wi-Fi radio/SSID reporting, internal-display brightness and Bluetooth radio control still need physical hardware/permission validation beyond the Windows CI environment.
  • Multi-display geometry exists, but broad physical multi-monitor hardware testing is still required.
  • Touchpad gestures, hot corner, notification ingestion and legacy tray compatibility remain future work.

Memory budget

Verified idle baseline: 15 MB

Windows CI launches the optimized release build and measures the FedoraWin process tree. The native-panel baseline has measured 15 MB idle with one FedoraWin process and no WebView2 children while idle.

The design target remains roughly 100 MB or less during normal idle use, with a hard automated ceiling of 300 MB. Rich WebView2 surfaces are temporary and should not stay resident after dismissal.

Latest iteration · September 19, 2026

Reusable control manager + real gallery publishing

Power Mode, Wi-Fi, Bluetooth and Wireless Pause now share one GNOME 51-style control-flyout manager for exclusivity, Escape handling, focus handoff, closing motion and accessibility state, while their native Windows backends remain separate.

  • The Power Mode flyout exposes Best Power Efficiency, Balanced and Best Performance through direct Windows power APIs.
  • Wi-Fi and Bluetooth now expose dedicated GNOME-style flyouts backed by real WLAN/WinRT state instead of generic shell placeholders.
  • Activities replaces its visible loading message with a neutral workspace preflight while native app/window data is resolved.
  • The Windows capture gate now targets thirteen distinct real FedoraWin.exe surfaces: panel, Activities, app grid, Terminal search, dark/light Quick Settings, Appearance, Power Mode, Wi-Fi, Bluetooth, Wireless Pause, date menu and a real native HWND frame.
  • Runtime screenshots and provenance are automatically published into the Pages gallery after a successful push gate.
  • Push and pull-request CI now use separate concurrency groups so PR verification cannot cancel the screenshot-publishing push run.

Immediate engineering priorities

  1. Validate Wi-Fi, internal-display brightness and Bluetooth radio control on physical laptop hardware, then evaluate system-wide Airplane Mode separately rather than claiming Wireless Pause is equivalent.
  2. Expand the real workspace identity layer into GNOME-style dynamic workspace and move behavior.
  3. Harden DWM thumbnail lifecycle, resize and multi-monitor placement.
  4. Continue search-provider architecture for apps, windows, settings and future providers.
  5. Implement safe Super-key behavior without breaking Windows shortcuts.
  6. Refine GNOME 51 transitions and interaction details under the existing memory budget.

Release gates

Automated Windows gate

Every native-branch push is checked for UI syntax, GNOME/UI contracts, Rust unit tests, cargo check, rustfmt, optimized release build, process-tree memory budget and real executable screenshot capture. A successful capture run also refreshes the public runtime gallery.

Still required before beta

Physical multi-monitor testing, mixed DPI, docking/hot-plug, high refresh displays, long-session recovery, touchpad behavior, broader device-control coverage and a coherent end-to-end GNOME 51 interaction pass.

A green build is necessary, not sufficient. FedoraWin will not be called beta until the Activities/workspace/dash/search/app-grid/calendar/Quick Settings experience and recovery behavior are coherent enough for local testing without treating the user’s Windows installation as the test harness.
