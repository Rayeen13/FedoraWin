Native window-chrome research · Stage 1 CI verified

Actual frame replacement, not a colour filter.

The goal is a faithful Adwaita-style headerbar on compatible standard Win32 apps, leaving custom-styled windows alone. FedoraWin-owned GTK4 windows use real libadwaita. A third-party window needs its own separately implemented native renderer and, potentially, a narrowly scoped opt-in helper inside its app process.

Stage 1 passed: real native frame attach and exact rollback

A disposable Win32 window has now passed Windows CI: its original Windows title bar was replaced by a native-painted Adwaita-style header, then restored, reattached, and restored again in the same running process. The original gate verifies unchanged Win32 style bits, draggable header, caption and resize hit targets, and original/restored screenshot equality. Later Windows CI runs also passed actual Windows-owned maximize/restore and minimize/restore system commands and caption double-click maximize/restore while attached; these are disposable-app proofs, not evidence of cross-process injection. Why a process-local frame layer?

Windows DWM can recolour captions and request rounded corners, but it cannot substitute the actual window controls or deliver an Adwaita-style headerbar on a third-party app. Non-client frame customization requires handling window messages such as WM_NCCALCSIZE and WM_NCHITTEST, rendering buttons and preserving move, resize and system actions. A narrow in-process component is a possible solution, subject to compatibility validation. It must not be represented as GTK widgets inside the foreign app.

Only suitable windows, only with consent

  • Opt-in, disabled by default. One test app first; then individually approved conventional windows.
  • Opera GX/Chromium-style windows, Firefox, GTK and other self-drawn titlebars, games and custom launchers remain excluded.
  • No Explorer, protected processes, security software, anti-cheat/DRM, elevated targets, system shell or cross-integrity attachment. Do not bypass Windows restrictions.
  • 64-bit and 32-bit require separately validated helpers; app-class exclusions are a conservative guard, not perfect custom-frame detection.

How the candidate engine would work

  1. Discover the HWND and verify its window class, owning thread, process identity and consent from outside the app.
  2. Attach only to that app's approved GUI thread. Save original frame-related values before any change; never subclass its window from the FedoraWin process.
  3. Render Adwaita-style non-client controls while retaining native move, resize, system menu, keyboard, Snap and mixed-DPI behavior.
  4. Disable and restore on the owning GUI thread; drain callbacks before unloading code. Fall back to the current reversible DWM styling, or leave the window untouched.

FedoraWin-owned windows use the tested real GTK4/libadwaita proof rather than this foreign-window mechanism.

Rollback and the no-reboot goal

Target: turn the effect off and restore the original frame without restarting Windows or Explorer and without restarting the target app on a healthy normal path. The helper must be able to decline or detach per window.

Limits: an app crash, hang or active in-process callback may prevent immediate unloading; that app might need to be closed and reopened. Microsoft explicitly notes that an unhooked callback can remain in progress. No absolute promise of restart-free removal is credible before actual tests.

Why this should not patch Windows or your files

The proposed design makes no changes to System32, uxtheme, Explorer binaries, drivers, boot files or machine-wide theme registries. It is not intended to inspect documents, passwords or app databases, and it requires narrow, documented IPC and a reviewable, signed helper. However, in-process code shares the target app's privileges and can crash it. Bugs could lose unsaved work. No feature can honestly guarantee zero data or OS risk; exclusion, fail-closed design and testable recovery are mandatory.

What must pass before calling it working

Completed on the disposable lab app: same-GUI-thread attach → render → detach → reattach → detach, with the target PID unchanged, original window procedure and style bits restored, caption and resize hit regions checked and original/restored screenshots identical. Expanded CI additionally verifies native maximize/restore and minimize/restore commands. Inspect expanded Windows CI ↗ · Initial screenshot evidence ↗.

Not yet proven: attaching to an independent approved application; full move/resize/Snap interactions; disable, app exit and force-kill recovery; cross-app compatibility. Then come per-app checks for Windows caption buttons, Alt+Space, double-click, accessibility, mixed DPI, multimonitor and memory stability. Tests must verify Opera GX-like self-styled apps and protected targets received no helper at all. A green DWM or standalone libadwaita test does not qualify.
