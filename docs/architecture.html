Architecture & safety.

How FedoraWin gets close to GNOME without pretending Windows is Linux or crossing unsafe system boundaries.

On this pageDesign principleLayersNative windowsTop panelActivitiesQuick SettingsThemesSafety boundariesTesting

Design principle

FedoraWin is a shell layer. Windows remains the operating system, Explorer remains available, DWM remains the compositor, and ordinary applications remain ordinary Windows applications.

Native when behavior matters; custom when GNOME owns the experience.

That rule guides the project more than visual imitation does.

Layers

WPF shell surfaces

The top panel, Activities, app grid, calendar and Quick Settings are FedoraWin-owned UI surfaces built for precise shell interaction.

Win32 / DWM bridge

The native bridge tracks real HWNDs, applies supported DWM attributes, reserves desktop work area through AppBar behavior, and listens for relevant window events.

Windows platform services

FedoraWin delegates desktop switching, device state and operating-system behavior back to Windows rather than reimplementing system internals.

Native window frames

FedoraWin does not place a fake titlebar over another application's titlebar. Styling is applied to the real HWND through DWM-supported behavior so caption buttons, resizing, hit-testing, Snap and application ownership remain real.

Top panel and work area

The panel is treated as desktop chrome, not a floating overlay. FedoraWin reserves top work area so maximized windows should respect the panel instead of rendering behind it.

Activities and workspaces

Activities is the center of navigation: search, app access, workspaces and dash behavior converge there. Workspace controls currently map to Windows virtual desktop actions while FedoraWin continues toward richer live workspace/window presentation.

Quick Settings

Quick Settings should act in place when Windows exposes a safe direct API. If a reliable direct path is unavailable, FedoraWin should fail gracefully or open the appropriate system surface rather than inventing fake state.

Appearance and accents

Light, dark and system modes plus GNOME/libadwaita-inspired accents are propagated across shell controls. Native application styling is intentionally constrained by what DWM safely supports.

Safety boundaries

  • Never patch Windows system DLLs.
  • Never replace explorer.exe as a requirement.
  • Never install kernel drivers or background services merely to imitate GNOME.
  • Never depend on destructive registry or shell modifications.
  • Keep recovery tooling available and testable.
  • Prefer documented Windows APIs and reversible integration.

Testing gates

The project maintains regression checks for architecture and safety rules plus a Windows runner for PowerShell 5.1, WPF and native compile smoke testing. A passing local test suite is necessary but not sufficient for a release; Windows CI remains a release gate.
