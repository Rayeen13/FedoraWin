Native hybrid shell architecture

GNOME behavior. Native idle core. Rich surfaces on demand.

FedoraWin implements GNOME's desktop interaction model on Windows. The always-on shell path is native Rust/Win32; richer GNOME surfaces use Tauri/WebView2 only while open.

Layers

Native Rust / Win32 panel

The top panel is always resident and no longer requires an idle WebView2 process tree. It owns the persistent Activities, clock and system-status entry points.

Tauri + WebView2 on demand

Activities, App Grid, Calendar and Quick Settings remain HTML/CSS/JavaScript surfaces because they benefit from fast GNOME/libadwaita iteration. They are created when opened and destroyed when dismissed.

Rust + Win32 / DWM

Native code owns HWND enumeration, DWM styling and thumbnails, AppBar reservation, monitor geometry, virtual-desktop identity, WLAN calls, app discovery, lifecycle events and global hotkeys.

Memory model

The architecture intentionally avoids keeping WebView2 alive just to draw a 32px panel. Windows CI measures the full FedoraWin process tree. The latest native-panel snapshot verified at 17 MB idle and 17 MB sampled peak with one FedoraWin process and no WebView2 children at idle.

Budget

Normal idle target: roughly 100 MB or less. Hard automated ceiling: 300 MB. The CI memory job fails a build that crosses the hard ceiling.

Adwaita window frames

FedoraWin keeps each third-party application's real HWND, resize border and Snap behavior. DWM supplies matching Adwaita frame colors and rounded corners. A lightweight Win32 overlay covers only the DWM-reported caption-button bounds and draws circular Adwaita minimize, maximize/restore and close controls; clicks are forwarded to the original HWND as system commands. WinEvent notifications reposition the overlay when the target moves or changes, and the overlay plus FedoraWin DWM changes are cleaned up when FedoraWin exits.

Top panel

The panel is a native Win32 shell window. Windows AppBar APIs reserve the top work area on the owning monitor. Because the panel is native, it can stay resident with minimal memory overhead.

Activities runtime

Activities uses DWM thumbnail relationships to render live application content into FedoraWin's overview window. WinEvent hooks watch external window lifecycle changes and trigger refreshes; activation and close actions operate on the original HWNDs.

Workspace runtime

FedoraWin reads real Windows virtual-desktop IDs and current-desktop state through the documented Virtual Desktop Manager interface. Activities previous/next controls now switch the actual Windows virtual desktop. FedoraWin-initiated window moves are journaled so they can be explicitly undone; dynamic GNOME workspace creation/removal and drag transitions remain in progress.

Display model

The display layer enumerates monitor bounds, work area, effective DPI and primary status. Negative coordinates and super-ultrawide widths are preserved. A topology watcher reflows the native panel and any currently open shell surfaces.

Keyboard entry

Alt+F1 uses RegisterHotKey on a dedicated Win32 message-loop thread. Bare Super remains separate because Windows owns Win-key combinations; FedoraWin will not break Win+E, Win+R or Snap shortcuts just to claim a global Super key.

Quick Settings

The rule is direct supported API when Windows provides one, graceful fallback otherwise. Wi-Fi is currently backed by the WLAN API. Other controls are moving from UI scaffolding to native implementations incrementally.

Safety and reversibility

  • Explorer stays alive as Windows session/shell infrastructure.
  • No replacement of explorer.exe in the default build.
  • No system DLL patching or process injection.
  • No kernel drivers.
  • No permanent Windows service just to imitate shell behavior.
  • No destructive registry hacks to suppress Start/taskbar behavior.
  • Runtime reservations, hooks and shell surfaces must have cleanup/release paths.
  • FedoraWin-initiated workspace moves are tracked for undo.
Recovery rule

Close FedoraWin and normal Windows should still be there.
