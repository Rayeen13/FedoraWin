FedoraWin DE · GNOME 51 target · native hybrid shell architecture

GNOME behavior. Native idle core. Rich surfaces on demand.

FedoraWin DE implements the current GNOME 51 interaction model on Windows. FedoraWin Shell is the visible shell layer inside the DE. The always-on shell path is native Rust/Win32; richer GNOME surfaces use Tauri/WebView2 only while open. Shell host windows are transparent, preserving native desktop compositing around the rounded cards without replacing Explorer or modifying external application frames.

Layers

Native Rust / Win32 panel

The top panel is always resident and no longer requires an idle WebView2 process tree. It owns the persistent Activities, clock and system-status entry points.

Tauri + WebView2 on demand

Activities, App Grid, Calendar and Quick Settings remain HTML/CSS/JavaScript surfaces because they benefit from fast GNOME/libadwaita iteration. They are created when opened and destroyed when dismissed.

Rust + Win32 / DWM

Native code owns HWND enumeration, DWM styling and thumbnails, AppBar reservation, monitor geometry, virtual-desktop identity, WLAN, Core Audio, Power, internal-display brightness and Bluetooth radio APIs, app discovery, lifecycle events and global hotkeys.

GNOME 51 fidelity layer

A dedicated shell stylesheet sits after the base and libadwaita token layers. It controls GNOME 51 proportions and interaction details without taking ownership away from Windows HWNDs or changing the native safety boundary.

Memory model

The architecture intentionally avoids keeping WebView2 alive just to draw a 32px panel. Windows CI measures the full FedoraWin process tree. The current native-panel baseline has measured 15 MB idle with one FedoraWin process and no WebView2 children at idle.

Budget

Normal idle target: roughly 100 MB or less. Hard automated ceiling: 300 MB. The CI memory job fails a build that crosses the hard ceiling.

Window frames: DWM versus real Adwaita

Two separate technologies. FedoraWin-owned GTK4 windows can use real libadwaita widgets and GTK's Win32 backend. A native AdwApplicationWindow, AdwToolbarView and AdwHeaderBar proof compiled, launched and produced real Windows dark/light HWND captures. CI evidence ↗ · Source ↗. This optional proof has not yet replaced the production Tauri surfaces or been included in the 32 MB idle shell measurement.

FedoraWin keeps each third-party application's real HWND, resize border, native caption buttons and Snap behavior. DWM receives reversible appearance and rounded-corner preferences while Windows continues to own minimize/maximize/close hit testing, resizing, Snap Layouts, keyboard accessibility and the non-client area.

DWM corner and colour changes do not create a GTK headerbar or round Windows caption buttons. The current runtime does not inject into foreign apps. A separate optional in-process frame engine is now an engineering design, not yet implemented: it would render Adwaita-style native chrome for approved standard Win32 windows while leaving custom app titlebars untouched. Explicit FedoraWin Light and Dark modes can request matching native caption treatment. In System mode FedoraWin does not force dark captions; Windows remains authoritative for light/dark while FedoraWin keeps only compatible corner/border treatment.

FedoraWin Shell · top panel

The panel is a native Win32 shell window. Windows AppBar APIs reserve the top work area on the owning monitor so maximized and snapped applications do not sit underneath it. Because the panel is native, it can stay resident with minimal memory overhead.

Activities runtime

Activities uses DWM thumbnail relationships to render live application content into FedoraWin's overview window. WinEvent hooks watch external window lifecycle changes and trigger refreshes; activation and close actions operate on the original HWNDs. GNOME 51 spacing, search width, workspace-stage proportions, dash geometry, focus rings and reduced-motion behavior sit on top of this native-backed model.

The initial surface uses a neutral workspace preflight while native app/window data resolves rather than exposing a persistent loading message. Capture evidence is not marked ready until the Activities bootstrap and thumbnail sync attempt have completed.

Applications and search

Installed applications are discovered from Windows Start sources and indexed with aliases such as Terminal, Files and System Monitor. The current app page holds 24 entries and presents them as a GNOME-like 6×4 grid. CI contracts guard these proportions.

Workspace runtime

FedoraWin reads real Windows virtual-desktop IDs and current-desktop state through the documented Virtual Desktop Manager interface. Activities previous/next controls switch the actual Windows virtual desktop. FedoraWin-initiated window moves are journaled so they can be explicitly undone; dynamic GNOME workspace creation/removal and drag transitions remain in progress.

Display model

The display layer enumerates monitor bounds, work area, effective DPI and primary status. Negative coordinates and super-ultrawide widths are preserved. A topology watcher reflows the native panel and any currently open shell surfaces.

Keyboard entry

Alt+F1 uses RegisterHotKey on a dedicated Win32 message-loop thread. Bare Super remains separate because Windows owns Win-key combinations; FedoraWin will not break Win+E, Win+R or Snap shortcuts just to claim a global Super key.

Quick Settings and control flyouts

The rule is direct supported API when Windows provides one, graceful fallback otherwise. Wi-Fi uses the Windows WLAN API for radio state/control and WlanQueryInterface for the current connection SSID and adapter state; master volume uses Windows Core Audio, battery/AC state uses GetSystemPowerStatus, screenshot entry uses the Windows screenshot path and Power Mode uses the Windows user-configured AC/DC power-mode APIs.

Power Mode, Wi-Fi, Bluetooth and Wireless Pause now use a shared GNOME 51-style flyout manager for one-open-at-a-time behavior, Escape handling, focus handoff, closing motion and accessibility state, while native Rust performs the actual Windows changes. Internal-display brightness is backed by the Windows monitor WMI provider; Bluetooth state/control uses Windows.Devices.Radios and requests access only when the user toggles the radio. Wireless Pause orchestrates only Wi-Fi/Bluetooth with per-radio results and an in-memory restore journal. It does not alter Windows system-wide Airplane Mode, cellular radios or other radios. Physical hardware/permission validation remains required.

Runtime evidence pipeline

The Windows gate builds the release executable, runs its memory budget, then launches the real fedorawin.exe repeatedly to capture thirteen surfaces: panel, Activities, applications, search, dark/light Quick Settings, Appearance, Power Mode, Wi-Fi, Bluetooth, Wireless Pause, date menu and a separately created native HWND styled by FedoraWin.

Captures are checked for initialized visual content, distinct hashes and non-opaque outer popover corners compared with the neighboring desktop. A successful push publishes the images and provenance metadata into docs/assets/runtime on main, which the public site hydrates automatically.

Safety and reversibility

  • FedoraWin DE hides Explorer taskbar windows only for the active session and launches a recovery guardian before doing so.
  • Explorer stays alive as Windows session/shell infrastructure.
  • No replacement of explorer.exe in the default build.
  • No system DLL patching or process injection.
  • No kernel drivers.
  • No permanent Windows service just to imitate shell behavior.
  • No destructive registry hacks to suppress Start/taskbar behavior.
  • Runtime reservations, hooks and shell surfaces must have cleanup/release paths.
  • FedoraWin-initiated workspace moves are tracked for undo.
Automated proof

The native branch is gated by UI syntax/contracts, Rust tests/check/format, optimized release build, process-tree memory budget and real runtime screenshot capture. The exact latest successful SHA and Windows runner provenance are shown on the Gallery.

Recovery rule

Close FedoraWin DE and normal Windows should still be there; the recovery guardian restores the taskbar presentation.
