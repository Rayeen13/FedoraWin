Native shell architecture

Rust core. Web UI. Windows APIs.

FedoraWin keeps the UI easy to iterate while native behavior stays behind a Rust/Win32 boundary.

On this pageLayersWindow framesPanelDisplaysHotkeysQuick SettingsNext architectureSafety

Layers

HTML / CSS / JavaScript

GNOME-style shell surfaces are authored as web UI: panel, Activities, apps, calendar and Quick Settings.

Tauri + WebView2

Tauri creates the desktop surfaces and bridges JavaScript commands to the Rust backend without bundling an Electron-sized Chromium runtime.

Rust + Win32 / DWM

Native code owns HWND enumeration, DWM attributes, AppBar reservation, monitor geometry, WLAN calls, app discovery and global hotkeys.

Native window frames

FedoraWin does not draw fake overlays over application titlebars. DWM attributes are applied to eligible real HWNDs so Windows retains hit-testing, resize, caption buttons and Snap.

Top panel

The panel is a real shell window. Windows AppBar APIs reserve top work area based on the monitor that actually contains the panel.

Display model

The display layer enumerates monitor bounds, work area, effective DPI and primary status. Negative desktop coordinates and super-ultrawide widths are preserved. A topology watcher reflows the shell when the signature changes.

Keyboard entry

Alt+F1 uses RegisterHotKey on a dedicated Win32 message-loop thread. Bare Super remains a separate compatibility problem because Windows owns Win-key combinations; FedoraWin will not break Win+E, Win+R or Snap shortcuts merely to intercept one key.

Quick Settings

The rule is direct API when Windows provides a safe one, graceful fallback otherwise. Wi-Fi is currently backed by the WLAN API. Other controls are being moved from UI scaffolding to native implementations incrementally.

Next architecture step

The current polling pieces will evolve into an event-driven ShellRuntime with WinEvent hooks, cached HWND state and persistent DWM thumbnails. Search will also move behind provider interfaces so apps, windows, settings and future integrations stay decoupled.

Safety boundaries

  • Do not require replacing explorer.exe.
  • No system DLL patching.
  • No kernel drivers.
  • No Windows service merely for shell imitation.
  • No destructive registry hacks to suppress Start/taskbar behavior.
  • Prefer documented, reversible Windows APIs.
